## 1. Introduction: Coherence vs. Consistency

In shared-memory multiprocessors, correct parallel execution requires two distinct architectural guarantees: **Cache Coherence** and **Memory Consistency**.

```
┌────────────────────────────────────────────────────────────────────────┐
│                   COHERENCE vs. CONSISTENCY                            │
├────────────────────────────────────────────────────────────────────────┤
│ Cache Coherence:                                                       │
│ • Focuses on a SINGLE memory location.                                 │
│ • Answers: "WHAT value does a read return?"                            │
│ • Guarantees: Write serialization and eventual write propagation.      │
├────────────────────────────────────────────────────────────────────────┤
│ Memory Consistency:                                                    │
│ • Focuses on MULTIPLE memory locations accessed by MULTIPLE threads.   │
│ • Answers: "WHEN does a processor observe a write made by another?"    │
│ • Guarantees: Global ordering of reads and writes to different memory │
│   locations across different processors.                               │
└────────────────────────────────────────────────────────────────────────┘
```

Because processors communicate and synchronize via shared variables in memory, the fundamental question of memory consistency is:
> **In what order must a processor observe the data writes of another processor?**

Since the only mechanism to observe writes is through reads, consistency models define the **legally permissible orderings of reads and writes to different memory locations**.

---

## 2. The Motivating Consistency Dilemma

Consider two concurrent processes, $P_1$ and $P_2$, running on different processor cores with shared variables $A$ and $B$, both initially initialized to `0` and cached locally:

```
       Processor P1                     Processor P2
    ───────────────────              ───────────────────
    A = 0;                           B = 0;
    ...                              ...
    A = 1;                           B = 1;
L1: if (B == 0) ...              L2: if (A == 0) ...
```

### The Problem:
* **Intuitive / Sequential Expectation:**
  * Reaching `L1` implies `A = 1` has taken effect.
  * Reaching `L2` implies `B = 1` has taken effect.
  * Therefore, it should be **impossible** for both `if` conditions (`B == 0` and `A == 0`) to evaluate to **true simultaneously**. At least one processor must observe the write of the other.
* **Hardware Reality in Modern Out-of-Order / Buffered Systems:**
  * If write invalidations are delayed in write buffers, or if the processor allows subsequent reads to bypass pending writes to hide memory latency:
    1. $P_1$ issues `A = 1`, but the invalidation message for $A$ is buffered in the network/bus queue.
    2. $P_1$ proceeds immediately to execute `if (B == 0)` and reads its local cached copy of $B$ (`0`).
    3. Concurrently, $P_2$ issues `B = 1`, buffers its invalidation, and immediately executes `if (A == 0)`, reading its local cached copy of $A$ (`0`).
    4. **Result:** Both $P_1$ and $P_2$ observe the condition as `true` and enter the critical statement, violating program logic.

## 3. Sequential Consistency (SC)

Formulated by Leslie Lamport (1979), **Sequential Consistency** is the most intuitive memory model.

### 3.1 Formal Definition
> A multiprocessor system is sequentially consistent if the result of any execution is the same as though:
> 1. The operations of all the processors were executed in some **sequential order**, and
> 2. The operations of each individual processor appear in this sequence in the **program order** specified by its program.

Under Sequential Consistency:
* Every processor executes memory accesses strictly in program order.
* Memory accesses from different processors are arbitrarily interleaved globally, but never reordered within an individual thread.
* In the motivating example, SC forces `A = 1` to complete before `if (B == 0)` executes, and `B = 1` to complete before `if (A == 0)` executes, making it impossible for both conditions to be true.

```
P1 Operations:  [ A = 1 ] ──────────────► [ Read B ]
                               ▲
                      Arbitrary Global Interleaving
                               ▼
P2 Operations:  [ B = 1 ] ──────────────► [ Read A ]
```

---

### 3.2 Hardware Implementation of Sequential Consistency
To strictly enforce Sequential Consistency:
1. A processor must **delay the completion of any memory access** until all cache invalidations generated by that access are completed and explicitly acknowledged.
2. Alternatively, the hardware must **delay issuing the next memory access** until the previous memory access has completely finished.
3. Speculative execution, out-of-order memory execution, and store buffers bypassing loads across different addresses cannot be freely used without complex rollback hardware.

---

### 3.3 The Performance Cost of Sequential Consistency: Worked Numerical Problem

#### Problem Statement:
Suppose a multiprocessor system has the following latency parameters for a write miss:
* **Time to establish ownership:** $50\text{ clock cycles}$
* **Time to issue each invalidate message (after ownership):** $10\text{ clock cycles}$
* **Time for an invalidate to complete and be acknowledged:** $80\text{ clock cycles}$
* **Number of sharing processors:** $4\text{ other processors}$ share the cache block.

1. How long does a write miss stall the writing processor if the architecture strictly implements **Sequential Consistency** (assuming invalidates must be explicitly acknowledged)?
2. If the architecture could continue executing immediately after obtaining ownership (without waiting for invalidations to complete), how long would the write stall?

---

#### Step-by-Step Solution:

1. **Under Sequential Consistency (waiting for invalidations to complete):**
   * The writing processor must wait for ownership, the issuance of all invalidates, and the completion of the final invalidate acknowledgement.
   * Since invalidation requests can overlap in the network, the critical path is governed by the **last issued invalidate**:
     $$\text{Time to issue } 4 \text{ invalidates} = 4 \times 10\text{ cycles} = 40\text{ cycles}$$
   * The last invalidate finishes $80\text{ cycles}$ after it is issued.
   * Therefore, total write stall time is:
     $$\text{Total Stall}_{\text{SC}} = \text{Ownership Time} + \text{Time to Issue Last Invalidate} + \text{Acknowledgement Latency}$$
     $$\text{Total Stall}_{\text{SC}} = 50 + (10 + 10 + 10 + 10) + 80 = 50 + 40 + 80 = 170\text{ clock cycles}$$

2. **Under Relaxed Consistency (continuing after ownership):**
   * The processor resumes execution as soon as exclusive ownership is granted:
     $$\text{Total Stall}_{\text{Relaxed}} = \text{Ownership Time} = 50\text{ clock cycles}$$
   * With an aggressive store buffer, the processor can potentially continue execution with $0$ stall cycles if the write buffer is not full.

> **Takeaway:** Strict Sequential Consistency introduces a penalty of **$170\text{ cycles}$ vs. $50\text{ cycles}$** (more than a $3.4\times$ latency penalty), creating a severe bottleneck in scalable systems.

## 4. The Programmer's View: Data-Race-Free (DRF) Programs

To overcome the performance penalty of Sequential Consistency without burdening programmers with erratic hardware behaviors, computer architects adopted the **Data-Race-Free (DRF)** programming contract.

```
┌────────────────────────────────────────────────────────────────────────┐
│                   THE PROGRAMMER - ARCHITECTURE CONTRACT               │
├────────────────────────────────────────────────────────────────────────┤
│ Programmer's Obligation:                                               │
│ • Write properly synchronized programs (Data-Race-Free).               │
│ • Protect all shared variable reads and writes with synchronization    │
│   operations (locks, unlocks, barriers).                               │
├────────────────────────────────────────────────────────────────────────┤
│ Hardware Guarantee:                                                    │
│ • Hardware is free to reorder reads/writes aggressively to achieve    │
│   maximum performance.                                                 │
│ • To the programmer, the execution is GUARANTEED to appear as if it    │
│   ran on a strictly Sequentially Consistent (SC) machine!              │
└────────────────────────────────────────────────────────────────────────┘
```

### 4.1 Definition of a Synchronized (DRF) Program
A program is **synchronized (data-race-free)** if, in every possible execution, every conflicting pair of accesses to the same shared variable (where at least one access is a write) is separated by a pair of synchronization operations:
1. One synchronization operation executed **after the write** by the writing thread (e.g., `unlock()`), and
2. One synchronization operation executed **before the access** by the observing thread (e.g., `lock()`).

```
    Thread 1 (Writer)                       Thread 2 (Reader)
 ──────────────────────                  ──────────────────────
   Shared Write (X = 1)
          │
          ▼
   Release / Unlock (S)  ══════════════►   Acquire / Lock (S)
                                                  │
                                                  ▼
                                           Shared Read (X)
```

If accesses to shared data are not properly synchronized, a **data race** exists: the execution outcome becomes unpredictable because it depends on the exact clock-cycle speed and interconnect arbitration of the cores.

## 5. Classification of Relaxed Consistency Models

Relaxed consistency models allow memory operations to complete out of order. They are classified based on which of the four program-order constraints they relax:

1. **$\text{Read} \to \text{Read}$ ($R \to R$):** Program order between consecutive reads.
2. **$\text{Read} \to \text{Write}$ ($R \to W$):** Program order between a read followed by a write.
3. **$\text{Write} \to \text{Read}$ ($W \to R$):** Program order between a write followed by a read.
4. **$\text{Write} \to \text{Write}$ ($W \to W$):** Program order between consecutive writes.

Notation: $X \to Y$ indicates that operation $X$ must complete and be globally observed before operation $Y$ is issued.

```
                           TAXONOMY OF CONSISTENCY MODELS
                           
             Strict Orderings Maintained: [ R→R, R→W, W→R, W→W ]
                                  │
                                  ▼
                   Sequential Consistency (SC)
                                  │
                       Relax W→R  ▼
               Total Store Order (TSO) / Processor Consistency
               (x86, IBM S/370, SPARC TSO)
                                  │
                       Relax W→W  ▼
                    Partial Store Order (PSO)
                    (SPARC PSO)
                                  │
                       Relax R→R  ▼
                       Relax R→W
                    Weak Ordering (WO) / Release Consistency (RC)
                    (PowerPC, ARMv8, RISC-V, C/C++11)
```

---

### 5.1 Total Store Order (TSO) / Processor Consistency
* **Orderings Relaxed:** Relaxes **$W \to R$** only.
* **Orderings Maintained:** $R \to R$, $R \to W$, and $W \to W$.
* **Hardware Motivation:** Allows a processor to place a write into a store buffer and continue executing subsequent reads without stalling. Stores to the same thread are maintained in order ($W \to W$).
* **Architectures:** Used in **x86** (Intel Core, AMD Ryzen), IBM S/370, DEC VAX, and SPARC.
* **Programming Impact:** Because write-to-write ordering ($W \to W$) is preserved, many synchronized algorithms designed for SC execute correctly under TSO without requiring explicit memory barriers.

---

### 5.2 Partial Store Order (PSO)
* **Orderings Relaxed:** Relaxes **$W \to R$** and **$W \to W$**.
* **Orderings Maintained:** $R \to R$ and $R \to W$.
* **Hardware Motivation:** Allows multiple writes in the store buffer to commit to the cache hierarchy out of order (e.g., merging writes to different cache lines to optimize bus/interconnect bandwidth).
* **Architectures:** Supported in SPARC (PSO mode).

---

### 5.3 Weak Ordering (WO)
* **Orderings Relaxed:** Relaxes **all four data orderings** ($R \to R, R \to W, W \to R, W \to W$).
* **Mechanism:** 
  * Completely decouples ordinary data references from synchronization variables.
  * Ordinary data reads and writes can be aggressively reordered by the compiler and out-of-order execution logic.
  * Synchronization operations ($S$) act as full bidirectional barriers (fences):
    $$S \to W, \quad S \to R, \quad R \to S, \quad W \to S, \quad S \to S$$
  * All prior reads and writes must complete before a synchronization operation begins; no subsequent reads or writes can begin until the synchronization completes.
* **Architectures:** Used in PowerPC.

---

### 5.4 Release Consistency (RC)
Adopted by **RISC-V**, **ARMv8**, and the **ISO C/C++11** memory model specifications, Release Consistency provides the highest performance while ensuring correctness for data-race-free code.

#### The Core Insight:
Synchronization operations naturally split into two functionally distinct operations:
1. **Acquire ($S_A$):** Locks or barriers used to gain access to shared data (e.g., `pthread_mutex_lock`).
2. **Release ($S_R$):** Unlocks or barriers used to return shared access to other processors (e.g., `pthread_mutex_unlock`).

```
                      RELEASE CONSISTENCY ONE-WAY BARRIERS
                      
    Ordinary Memory Operations (Before Critical Section)
                 │
                 │ (Can migrate down past Acquire)
                 ▼
  ═══════════════════════════════════════════════════════════════
             ACQUIRE (SA: e.g., lock / load-acquire)
  ═══════════════════════════════════════════════════════════════
                 │
                 ▼ [CRITICAL SECTION]
                 • Shared Reads & Writes CANNOT migrate above SA
                 • Shared Reads & Writes CANNOT migrate below SR
                 ▲
  ═══════════════════════════════════════════════════════════════
             RELEASE (SR: e.g., unlock / store-release)
  ═══════════════════════════════════════════════════════════════
                 ▲
                 │ (Can migrate up before Release)
                 │
    Ordinary Memory Operations (After Critical Section)
```

#### Orderings Enforced by Release Consistency:
* **$S_A \to \text{Read} / \text{Write}$:** Ordinary reads and writes within the critical section **cannot move above the Acquire**.
* **$\text{Read} / \text{Write} \to S_R$:** Ordinary reads and writes within the critical section **cannot move below the Release**.
* **Relaxation:**
  * Reads/writes preceding an Acquire do *not* need to complete before $S_A$ completes.
  * Reads/writes following a Release do *not* need to wait for $S_R$ to finish.
  * Synchronization orderings are maintained: $S_A \to S_A, S_A \to S_R, S_R \to S_A, S_R \to S_R$.

## 6. Comprehensive Comparison of Consistency Models (Table 5.23)

The following table summarizes the ordinary and synchronization orderings enforced across the five consistency models:

| Memory Consistency Model | Architectures / Implementations | Ordinary Data Access Orderings Maintained | Synchronization Access Orderings Maintained |
|:---|:---|:---|:---|
| **Sequential Consistency (SC)** | Most machines as an optional debug/strict mode | $R \to R, \; R \to W, \; W \to R, \; W \to W$ | $S \to W, \; S \to R, \; R \to S, \; W \to S, \; S \to S$ |
| **Total Store Order (TSO) / Processor Consistency** | x86 (Intel / AMD), IBM S/370, DEC VAX, SPARC TSO | $R \to R, \; R \to W, \; W \to W$ <br> *(Relaxes $W \to R$)* | $S \to W, \; S \to R, \; R \to S, \; W \to S, \; S \to S$ |
| **Partial Store Order (PSO)** | SPARC PSO | $R \to R, \; R \to W$ <br> *(Relaxes $W \to R, \; W \to W$)* | $S \to W, \; S \to R, \; R \to S, \; W \to S, \; S \to S$ |
| **Weak Ordering (WO)** | PowerPC | *None* <br> *(Relaxes all four data orderings)* | $S \to W, \; S \to R, \; R \to S, \; W \to S, \; S \to S$ |
| **Release Consistency (RC)** | RISC-V, ARMv8, ISO C/C++11 standards | *None* <br> *(Relaxes all four data orderings)* | $S_A \to W, \; S_A \to R, \; R \to S_R, \; W \to S_R,$ <br> $S_A \to S_A, \; S_A \to S_R, \; S_R \to S_A, \; S_R \to S_R$ |

## 7. Comparative Example: Ordering Constraints in Action (Figure 5.24)

Consider an execution thread performing a mix of ordinary memory operations and synchronization primitives:

```
Instruction Sequence:
    1:       = A      (Read A)
    2:   B =          (Write B)
    3:   acquire(S);  (SA)
    4:   C =          (Write C)
    5:       = D      (Read D)
    6:   release(S);  (SR)
    7:   E =          (Write E)
    8:   F =          (Write F)
```

The table below contrasts the minimal ordering constraints imposed by each model (transitive orderings omitted):

```
(1) Sequential Consistency (SC)
    [ Read A ] ──► [ Write B ] ──► [ acquire(S) ] ──► [ Write C ] ──► [ Read D ] ──► [ release(S) ] ──► [ Write E ] ──► [ Write F ]
    (Every memory operation is strictly ordered to its successor)

(2) Total Store Order (TSO)
    • Preserves R→R, R→W, W→W, and all S orderings.
    • Write B cannot move past acquire(S).
    • acquire(S) cannot move past Write C.
    • Write C must complete before Read D.
    • release(S) cannot move past Write E; Write E must precede Write F.
    • (Only W→R without intervening S can be relaxed).

(3) Partial Store Order (PSO)
    • Like TSO, but consecutive writes can reorder (W→W relaxed).
    • Write E and Write F can commit out of order.
    • Synchronization points acquire(S) and release(S) still enforce boundaries.

(4) Weak Ordering (WO)
    • Data accesses between synchronization points can float freely.
    • All accesses before acquire(S) (Read A, Write B) must complete before acquire(S).
    • All accesses inside critical section (Write C, Read D) must complete before release(S).
    • Accesses after release(S) (Write E, Write F) cannot start until release(S) completes.

(5) Release Consistency (RC)
    • FEWEST constraints of all five models:
      1. acquire(S) forces: acquire(S) ──► Write C   and   acquire(S) ──► Read D
         (Operations inside critical section cannot move above acquire)
      2. release(S) forces: Write C ──► release(S)   and   Read D ──► release(S)
         (Operations inside critical section cannot move below release)
      3. acquire(S) ──► release(S) ordering is preserved.
      4. Operations BEFORE acquire (Read A, Write B) can overlap downward past acquire!
      5. Operations AFTER release (Write E, Write F) can overlap upward before release!
```

## 8. Memory Fences and Barriers

When programmers require explicit ordering of memory operations without calling heavy library synchronization routines (such as mutual exclusion locks), modern architectures provide **Memory Fence / Barrier instructions**.

A memory fence forces the processor to guarantee that all specified memory operations issued before the fence are globally completed and visible before any memory operations following the fence can be issued.

### Architectural Implementations:
1. **RISC-V (`FENCE`):**
   * Format: `FENCE predecessor_set, successor_set`
   * Specifies fine-grained ordering between Read (`r`), Write (`w`), Input (`i`), and Output (`o`):
     ```assembly
     FENCE   rw, rw      # All previous reads & writes must complete before subsequent reads & writes
     FENCE   w, w        # Write-only fence: enforces write-to-write ordering (like store buffer drain)
     FENCE   r, r        # Read-only fence
     ```
2. **ARMv8:**
   * `DMB` (Data Memory Barrier): Ensures that memory accesses before the barrier are observed before memory accesses after the barrier.
   * `DSB` (Data Synchronization Barrier): Halts execution of all subsequent instructions until all pending memory transactions complete.
   * `ISB` (Instruction Synchronization Barrier): Flushes pipeline and prefetch buffers.
3. **x86:**
   * `MFENCE` (Memory Fence): Serializes all load and store operations.
   * `SFENCE` (Store Fence): Serializes store operations (ensures store buffer drains).
   * `LFENCE` (Load Fence): Serializes load operations and speculative execution.
